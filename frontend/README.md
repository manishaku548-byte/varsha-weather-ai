# VARSHA Weather AI — Decision-Support Dashboard (Phase 5/6)

Single-page Next.js dashboard for the VARSHA Weather AI backend
(SIH26081). **Decision-Support Prototype — Synthetic Development Dataset —
Not an Official Weather Warning.**

## Requirements

- Node.js ≥ 20 (developed with Node 25 / npm 11)
- The FastAPI backend running on `http://127.0.0.1:8001` (see the repo root README)

## Setup

```powershell
cd frontend
npm install
copy .env.example .env.local   # adjust NEXT_PUBLIC_API_BASE_URL if needed
npm run dev
```

Open **http://localhost:3000**.

## How it works

- **Backend is the source of truth.** No forecast, weight, confidence, risk or
  metric value is computed or hardcoded in the frontend. Every number comes from
  the typed client in `lib/api.ts` (`GET /forecast`, `GET /forecast/explain`,
  `POST /forecast/simulate-source-failure`, `GET /backtest[/report]`,
  `GET /model/status`, `GET /model/report`, `POST /overrides`,
  `GET /audit-logs`, …).
- **Districts** come only from `GET /districts`; the date picker is bounded by
  `GET /data/summary` (`first_valid_date` → `last_valid_date`).
- The dashboard never decides "winners": the validation table only highlights a
  method when the backend `comparison_summary` reports it as best, and it never
  colours VARSHA as best on its own.
- CSV reports are always generated by the backend
  (`GET /backtest/report?format=csv`), fetched as a blob and downloaded
  locally — never assembled client-side.
- AI-source provenance (`trained_local_correction_model` vs
  `fallback_precomputed_ai_source`) is shown exactly as the backend reports it,
  so a trained model is never presented as something it is not.
- Error surfaces are user-readable: FastAPI `detail` payloads are parsed into
  `ApiError` objects; raw stack traces are never rendered.

## Map

The district map (`components/DistrictMapInner.tsx`) uses react-leaflet with a
light CARTO basemap (online tile service). District markers and labels are local
data from `GET /districts`. If the tile service is unreachable, markers and the
selection ring still render on a plain background; the card notes it is
"not an official warning map".

## Local roles (demo only)

The role selector in the header is a **local simulation**, not authentication:

- **Viewer** — read-only; override/audit section hidden.
- **Forecaster** — can record expert overrides (`POST /overrides`).
- **Administrator** — forecaster + live "Train model" demo action
  (`POST /model/train`).

Overrides and the audit timeline are stored locally in the backend SQLite
database and labelled as a *prototype local review log — not an official
authorization record*.

## Demo aid (Phase 6)

- The slim **"Suggested 3-minute demo flow"** strip (Forecast → Why this
  forecast → Backtest → Source failure → Expert override) sits under the
  controls. Its **Load Demo Scenario** button only sets existing inputs
  (Prayagraj · 2025-09-03 · 24 h, from `lib/constants.ts`) and triggers the
  normal debounced `GET /forecast` + `GET /forecast/explain` run — it injects
  nothing and bypasses no backend call.
- **Copy Summary** (forecast hero header) copies the backend-returned values
  plus the disclaimer to the clipboard — no client-side computation.
- **Print (Ctrl+P)** prints the forecast/validation summary; controls, map,
  simulators and review panels are hidden via `print:hidden` classes + the
  `@media print` block in `app/globals.css`.
- Simulated source-failure state is local-only and is cleared whenever the
  district / date / lead changes or the page reloads — it never persists as a
  corrupted state (see `docs/demo_scenario.md` for expected values).

## Backend connection troubleshooting

| Symptom | Fix |
| --- | --- |
| Header shows "Backend unavailable" with the URL | The backend is not reachable on that URL. Start it on `127.0.0.1:8001` (see root README), then click **Retry connection** — the banner also auto-recovers via health polling. |
| Changed `NEXT_PUBLIC_API_BASE_URL` has no effect | Restart `npm run dev` — the value is baked into the client bundle at build/dev time from `frontend/.env.local` (copy from `.env.example`). |
| Browser console shows CORS errors | Confirm the backend allows the dashboard origin: the default `VARSHA_CORS_ORIGINS` includes `http://localhost:3000` and `http://127.0.0.1:3000`. |
| 404 on district / date | The date must sit inside the backend dataset window (the picker is bounded by `GET /data/summary`); districts come only from `GET /districts`. |
| Forecast shows `fallback_precomputed_ai_source` | No trained artifact for that horizon (or inference disabled). Check `GET /model/status` for the exact reason and train via `POST /model/train` if desired — the fallback is a disclosed, first-class state, not an error. |
| Port 3000 busy | Run `npm run dev -- -p 3100` and adjust the backend `VARSHA_CORS_ORIGINS` accordingly. |

## Deployment (Vercel)

- The dashboard deploys on **Vercel** with root directory `frontend`; no
  `vercel.json` is required — Next.js defaults are used.
- Set one environment variable in the Vercel project (all environments):
  `NEXT_PUBLIC_API_BASE_URL=https://<your-backend>.onrender.com` (exact
  backend public URL, no trailing slash). It is baked in at **build time** —
  changing it requires a redeploy (Vercel does that automatically).
- If the deployed backend is unreachable or the variable is wrong, the page
  shows the *Backend unavailable* banner with the exact polled URL and a
  **Retry connection** button — it never crashes or renders blanks.
- Full step-by-step runbook (GitHub → Vercel + Render/Railway, env vars,
  CORS, free-tier caveats, model fallback): **`../docs/DEPLOYMENT.md`**. The
  mandatory prototype/disclaimer banner is part of the production build and is
  identical on Vercel.
